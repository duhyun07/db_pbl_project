문제 4

상태 변경 → patch_history 자동 기록

담당 ①③ 채점 선행 #0, #3

PROBLEM · 문제

담당자가 조치 건의 상태를 바꾸는 UPDATE를 작성한다. 이력은 트리거가 자동으로 남기므로 patch_history에 직접 INSERT하지 않는다. 변경자(changed_by)가 정확히 기록되고, patched로 바꿀 때는 완료 시각도 함께 저장돼야 한다.

IO · 입력과 출력

입력

sql/q04.sql: UPDATE 문 1개. 파라미터는 이름 있는 자리로: %(sv_id)s, %(new_status)s, %(staff_id)s(바꾸는 사람), %(changed_at)s(바꾼 시각).

출력

채점기가 UPDATE 뒤에 (1) 해당 조치 건의 이력 old_status, new_status, changed_by를 history_id 순으로, (2) 조치 건의 status, patched_at, updated_by를 조회해 비교한다.

LIMIT · 제한

  • NOW() 대신 %(changed_at)s 사용 (결과가 날짜에 따라 바뀌지 않게)
  • patch_history에 직접 INSERT 금지 (트리거 전용)
  • patched가 아닌 상태로 바꿀 때는 patched_at을 바꾸지 않는다

EXAMPLE · 예제

파라미터: sv_id = 1, new_status = in_progress, staff_id = 1, changed_at = 2026-11-25 15:30:00

이 밖에 숨은 케이스가 2개 있어요. 숨은 케이스가 틀리면 입력은 보여 주지 않고 "숨은 케이스 n"이라고만 나와요.

NOTE · 노트

  • 케이스 1에서 이전 변경자는 3번이에요. UPDATE에서 updated_by를 빼먹으면 이력의 changed_by가 3으로 남아 틀려요.
  • 케이스 2에서 patched_at을 안 넣으면 CHECK 오류 3819(런타임 에러)가 나요.
  • 상태가 그대로면(open → open) 트리거는 이력을 남기지 않아요.

HINT · 힌트 (관련 수업)

정답 대신 다시 볼 수업 주차예요. 수업에 없던 문법은 공통 가이드의 미니 사전에 있어요.

  • 2주차 UPDATE
  • 6주차 FK NULL

JUDGE · 채점 방법

제출 파일 sql/q04.sql을 만든 뒤 실행해요. 맞았습니다!!가 나오면 다음 문제로 넘어가요. 채점기는 케이스마다 ROLLBACK해서 DB를 바꾸지 않아요.

RESET · 이 단계 시작 상태로 되돌리기

채점기는 케이스마다 ROLLBACK해서 DB를 바꾸지 않아요. 직접 실험하다 데이터가 바뀌었으면 schema·seed 다시 적재 (공통 가이드의 명령, Plan B는 Workbench에서 schema.sql → seed.sql 실행)

# Docker (레포 루트, 기존 데이터는 모두 지워져요)
docker compose exec db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 < /work/db/schema.sql && mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 < /work/db/seed.sql'
