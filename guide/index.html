WHAT · 무엇을 만드나

Ubuntu 보안 취약점·패치 관리 DB 시스템

Ubuntu 24.04 서버에 깔린 Apache, OpenSSH의 보안 취약점(CVE)과 위험도(CVSS), Ubuntu 패키지별 수정 상태를 DB에 넣고, 서버별로 누가 · 언제까지 · 어떤 상태로 조치하고 있는지 관리합니다.

CVE와 패치 정보는 실제 데이터(10~15건), 서버·담당자·조치 이력은 가상 데이터를 씁니다.

이것만은 기억하기

  • 메인은 DB 설계와 SQL이에요. Python은 그걸 보여주는 도구고요.
  • LLM은 시간이 남을 때 붙이는 추가 기능이에요. LLM 없이도 시연이 다 돼야 합니다.
  • 기존 보안 도구(Wazuh, Trivy 등)를 대체하려는 게 아니에요. 자동 스캔이나 자동 패치는 안 만듭니다.

GRADING · 교수님 채점 기준과 우리 대응

교수님 기준우리가 보여줄 것주 담당
1. DB로 어떤 문제를 해결하나"새 OpenSSH 취약점이 나왔다 → 어느 서버가 영향받고, 누가 언제까지 조치하고, 지금 몇 %나 끝났나?"를 쿼리 몇 개로 답한다전원
2. 데이터를 어떻게 모아서 정리했나NVD·Ubuntu JSON 수집 → 필드-컬럼 매핑 문서 → ERD·정규화 → 가상 데이터 생성 규칙④, ①
3. SQL 정확성·다양성·효율성분석 쿼리 6~7개(JOIN, GROUP BY, HAVING, CASE, 서브쿼리), 트리거·뷰, 대량 데이터에서 인덱스 전후 EXPLAIN 비교②, ①
4. 실제로 효율적이고 쓸모 있나기존 방식(서버마다 접속해서 버전 확인 → 엑셀 정리) vs 쿼리 실행 시간 비교, 자동 이력 기록②, ③

VALUES · 상태값 (모두 이 값만 쓰기)

Ubuntu 패키지 상태

cve_package_status.status

  • released 수정 패키지가 나옴 (fixed_version 필수)
  • needed 영향 있음, 아직 수정 안 됨
  • not-affected 영향 없음
  • deferred / ignored 보류·무시

서버별 조치 상태

system_vulnerabilities.status

  • open 확인됨, 아직 착수 안 함
  • in_progress 조치 중
  • patched 패치 완료 (patched_at 필수)
  • risk_accepted 위험 수용 (조치 안 하기로 결정)

RULES · 협업 규칙

Git

  • feature/역할-작업명 브랜치에서 작업 → PR로 main에 합치기
  • 작업 시작 전에 git pull 먼저
  • git add . 대신 내가 바꾼 파일만 골라서 add
  • .env, 비밀번호, API 키는 절대 커밋 금지

데이터

  • 실제 데이터(CVE)와 가상 데이터는 섞지 않기
  • CVSS나 패치 정보가 없으면 지어내지 말고 NULL
  • 테이블·컬럼 이름은 snake_case, docs/db_dictionary.md 기준
  • 스키마를 바꿔야 하면 ①에게 먼저 말하기 (다른 사람 코드가 깨져요)
