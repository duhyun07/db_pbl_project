2질문 하나를 쿼리로 바꾸는 절차

① 이 단계에서 만드는 것

② 왜 이렇게 하나

SELECT
  s.hostname,
  sv.cve_id,
  v.cvss_score,
  sv.status,
  sv.due_date,
  DATEDIFF(CURDATE(), sv.due_date) AS days_overdue,
  COALESCE(st.name, '(미배정)')     AS assignee
FROM system_vulnerabilities sv
JOIN systems         s  ON s.system_id = sv.system_id
JOIN vulnerabilities v  ON v.cve_id    = sv.cve_id
LEFT JOIN staff      st ON st.staff_id = sv.assignee_id
WHERE sv.status IN ('open', 'in_progress')
  AND sv.due_date < CURDATE()
ORDER BY days_overdue DESC, v.cvss_score DESC;

③ 코드

완성 쿼리 — Q4 Apache vs OpenSSH 취약점 수·위험도 분포

-- 24.04 기준으로 소프트웨어별 CVE 수와 CVSS 구간별 개수
SELECT
  sw.name                                                AS software,
  COUNT(DISTINCT cps.cve_id)                             AS cve_count,
  ROUND(AVG(v.cvss_score), 2)                            AS avg_cvss,
  SUM(v.cvss_score >= 9.0)                               AS critical_cnt,
  SUM(v.cvss_score >= 7.0 AND v.cvss_score < 9.0)        AS high_cnt,
  SUM(v.cvss_score >= 4.0 AND v.cvss_score < 7.0)        AS medium_cnt,
  SUM(v.cvss_score <  4.0)                               AS low_cnt,
  SUM(v.cvss_score IS NULL)                              AS no_score_cnt
FROM software sw
LEFT JOIN cve_package_status cps
       ON cps.software_id = sw.software_id AND cps.ubuntu_release = '24.04'
LEFT JOIN vulnerabilities v ON v.cve_id = cps.cve_id
GROUP BY sw.software_id, sw.name
ORDER BY sw.name;
software           | cve_count | avg_cvss | critical_cnt | high_cnt | medium_cnt | low_cnt | no_score_cnt
Apache HTTP Server |         3 |     6.47 |            1 |        0 |          2 |       0 |            0
OpenSSH            |         2 |     7.50 |            0 |        1 |          0 |       0 |            1

SUM(조건)은 MySQL에서 조건이 참이면 1, 거짓이면 0이라 "조건에 맞는 개수"가 돼요. CASE WHEN … THEN 1 ELSE 0 END와 같은 뜻이니, 발표 자료에는 CASE 버전으로 바꿔 써도 돼요.

4-4. 완료율의 0으로 나누기

SELECT 3 / 0 AS plain_div, 3 / NULLIF(0, 0) AS with_nullif;
plain_div | with_nullif
NULL      | NULL

MySQL의 SELECT는 0으로 나누면 에러 대신 NULL을 내요. 그래도 NULLIF(COUNT(…), 0)를 쓰는 이유는 "조치 건이 0인 서버는 완료율이 없다(NULL)"는 의도를 쿼리에 드러내기 위해서예요. ①의 뷰도 같은 방식이고, ③은 NULL을 0%가 아니라 빈칸으로 보여줘요.

4-5. 날짜 비교

-- due_date는 DATE, detected_at·patched_at은 DATETIME
-- DATETIME에 BETWEEN '…-01' AND '…-30'을 쓰면 30일 0시 이후가 빠짐
SELECT CAST('2026-11-30 15:00:00' AS DATETIME) BETWEEN '2026-11-01' AND '2026-11-30' AS between_result,
       (CAST('2026-11-30 15:00:00' AS DATETIME) >= '2026-11-01'
        AND CAST('2026-11-30 15:00:00' AS DATETIME) < '2026-12-01')            AS half_open_result;

-- 기한 초과 일수: DATEDIFF(큰 날짜, 작은 날짜)
SELECT sv_id, due_date, DATEDIFF(CURDATE(), due_date) AS days_overdue
FROM system_vulnerabilities WHERE due_date < CURDATE();
between_result | half_open_result
             0 |                1

위 출력과 같은 숫자가 나오면 돼요. 특히 4-1의 9 / 5 / 3은 seed 주석의 표(조치 건 9개, CVE 5종, 서버 3대)와 맞아야 해요.

⑤ 막히기 쉬운 부분

증상원인해결
WHERE cvss_score = NULL이 0행NULL은 =로 비교 안 됨IS NULL / IS NOT NULL

⑥ 다음 사람에게 넘길 것

-- =====================================================================
-- vuln_mgmt 분석 쿼리 (담당: ②)
-- 실행: docker compose exec -T db mysql --default-character-set=utf8mb4 \
--         -u vuln_app -p vuln_mgmt < sql/analysis_queries.sql
-- 기준 데이터: db/seed.sql (가짜 데이터)
-- =====================================================================
USE vuln_mgmt;

-- ---------------------------------------------------------------------
-- Q5. 처리 기한을 넘긴 미해결 건과 담당자는?
-- 사용 기능: JOIN 2개 + LEFT JOIN(담당자 없음), DATEDIFF, COALESCE, ORDER BY 2단
-- NULL 처리: 기한(due_date)이 NULL인 건은 "기한 없음"이라 제외
-- 파라미터: 없음
-- catalog id: q5_overdue_open
-- seed 기댓값: 2행 (sv 1, sv 2)
-- ---------------------------------------------------------------------
SELECT
  s.hostname,
  sv.cve_id,
  v.cvss_score,
  sv.status,
  sv.due_date,
  DATEDIFF(CURDATE(), sv.due_date) AS days_overdue,
  COALESCE(st.name, '(미배정)')     AS assignee
FROM system_vulnerabilities sv
JOIN systems         s  ON s.system_id = sv.system_id
JOIN vulnerabilities v  ON v.cve_id    = sv.cve_id
LEFT JOIN staff      st ON st.staff_id = sv.assignee_id
WHERE sv.status IN ('open', 'in_progress')
  AND sv.due_date < CURDATE()
ORDER BY days_overdue DESC, v.cvss_score DESC;

8-2. 측정 스크립트 sql/benchmark.py

"""쿼리를 여러 번 실행해서 평균 실행 시간을 잰다.

실행: python sql/benchmark.py --label before --repeat 20
출력: docs/performance.md 표에 그대로 붙일 수 있는 마크다운 행
"""
import argparse
import os
import statistics
import time
from pathlib import Path

import pymysql
from dotenv import load_dotenv

load_dotenv(Path(__file__).resolve().parent.parent / ".env")

# 측정할 쿼리. 이름: SQL
QUERIES = {
    # 결과 행이 많으면 "결과를 받아 오는 시간"이 대부분이 되어 인덱스 효과가 가려진다.
    # 그래서 같은 조건을 COUNT(*)로 세어서 DB가 행을 찾는 시간만 비교한다.
    "Q5 기한 초과 미해결 (COUNT)": """
        SELECT COUNT(*)
        FROM system_vulnerabilities sv
        WHERE sv.status IN ('open', 'in_progress') AND sv.due_date < CURDATE()""",
    "서버별 미해결 수 (JOIN + GROUP BY)": """
        SELECT s.system_id, s.hostname, COUNT(sv.sv_id) AS unresolved
        FROM systems s
        LEFT JOIN system_vulnerabilities sv
               ON sv.system_id = s.system_id AND sv.status IN ('open', 'in_progress')
        GROUP BY s.system_id, s.hostname""",
    "서버별 미해결 수 (상관 서브쿼리)": """
        SELECT s.system_id, s.hostname,
               (SELECT COUNT(*) FROM system_vulnerabilities sv
                 WHERE sv.system_id = s.system_id AND sv.status IN ('open', 'in_progress')) AS unresolved
        FROM systems s""",
}


def connect():
    return pymysql.connect(
        host=os.getenv("MYSQL_HOST", "127.0.0.1"),
        port=int(os.getenv("MYSQL_PORT", "3306")),
        user=os.getenv("MYSQL_USER"),
        password=os.getenv("MYSQL_PASSWORD"),
        database=os.getenv("MYSQL_DATABASE", "vuln_mgmt"),
        charset="utf8mb4",
    )


def measure(cur, sql, repeat):
    cur.execute(sql)          # 첫 실행은 버리기 (데이터가 메모리에 올라오는 시간 제외)
    cur.fetchall()
    times = []
    for _ in range(repeat):
        start = time.perf_counter()
        cur.execute(sql)
        rows = cur.fetchall()   # 결과를 다 받아 와야 실제 실행이 끝난 것
        times.append((time.perf_counter() - start) * 1000)
    return len(rows), statistics.mean(times), min(times), max(times)


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--label", required=True, help="예: before, after-idx1")
    parser.add_argument("--repeat", type=int, default=20)
    args = parser.parse_args()

    conn = connect()
    with conn.cursor() as cur:
        cur.execute("SELECT VERSION()")
        version = cur.fetchone()[0]
        cur.execute("SELECT COUNT(*) FROM system_vulnerabilities")
        sv_count = cur.fetchone()[0]
        print(f"MySQL {version}, system_vulnerabilities {sv_count}행, 반복 {args.repeat}회\n")
        print("| 쿼리 | 조건 | 결과 행 | 평균(ms) | 최소(ms) | 최대(ms) |")
        print("|---|---|---|---|---|---|")
        for name, sql in QUERIES.items():
            rows, avg, mn, mx = measure(cur, sql, args.repeat)
            print(f"| {name} | {args.label} | {rows} | {avg:.2f} | {mn:.2f} | {mx:.2f} |")
    conn.close()


if __name__ == "__main__":
    main()

9성능: 인덱스 추가와 재측정

① 이 단계에서 만드는 것

내 로컬 DB에서 인덱스를 실험한 결과(after)와 추천 인덱스 목록.

② 왜 이렇게 하나

인덱스는 스키마의 일부라서 db/schema.sql은 ①만 고쳐요. ②는 로컬에서 실험하고 "이 인덱스를 넣으면 이만큼 빨라진다"는 근거와 함께 ①에게 추천해요.

인덱스 후보를 고르는 기준

  • WHERE·JOIN·ORDER BY에 자주 나오는 컬럼. 우리 쿼리는 대부분 status IN (…)과 due_date를 같이 써요.
  • 복합 인덱스 순서: = 또는 IN으로 비교하는 컬럼을 앞에, 범위(<, BETWEEN)로 비교하는 컬럼을 뒤에 → (status, due_date).
  • 이미 있는 인덱스는 빼기: InnoDB는 FK 컬럼에 인덱스를 자동으로 만들어요. system_id, cve_id, assignee_id, updated_by, hostname(UNIQUE)에는 이미 있어요. SHOW INDEX FROM system_vulnerabilities;로 확인.
  • 작은 테이블(vulnerabilities는 CVE 10~15행)은 인덱스를 걸어도 효과가 없어요.

③ 코드

-- 인덱스 추가 (내 로컬 DB에서만)
CREATE INDEX idx_sv_status_due ON system_vulnerabilities (status, due_date);

-- 실험을 되돌릴 때
DROP INDEX idx_sv_status_due ON system_vulnerabilities;

10성능: 쿼리 작성 방식 비교

① 이 단계에서 만드는 것

같은 질문을 두 가지 방식으로 쓴 쿼리 쌍과, 결과·시간 비교.

② 왜 이렇게 하나

"어떻게 써도 결과는 같다"가 아니라 결과가 달라지는 경우(NOT IN과 NULL)와 시간이 달라지는 경우(JOIN vs 상관 서브쿼리)를 직접 보여주면 SQL을 이해하고 쓴다는 근거가 돼요.

③ 코드

10-1. JOIN + GROUP BY vs 상관 서브쿼리 — benchmark.py의 QUERIES에 이미 두 버전이 들어 있어요. 결과 행 수(20000)가 같은지 먼저 보고 시간을 비교해요.

10-2. NOT IN vs NOT EXISTS — "맡은 건이 하나도 없는 담당자"를 찾을 때. 데이터를 건드리니 트랜잭션 안에서 하고 ROLLBACK해요.

START TRANSACTION;
INSERT INTO staff (staff_id, name, team, email)
VALUES (99, '임시담당', '테스트', 'temp@example.com');    -- 맡은 건이 없는 담당자

-- NOT IN: assignee_id에 NULL이 하나라도 있으면 결과가 0행이 됨
SELECT COUNT(*) AS not_in_rows
FROM staff
WHERE staff_id NOT IN (SELECT assignee_id FROM system_vulnerabilities);

-- NOT EXISTS: NULL과 상관없이 의도대로
SELECT COUNT(*) AS not_exists_rows
FROM staff st
WHERE NOT EXISTS (SELECT 1 FROM system_vulnerabilities sv WHERE sv.assignee_id = st.staff_id);

-- NOT IN을 고친 버전
SELECT COUNT(*) AS not_in_fixed
FROM staff
WHERE staff_id NOT IN (SELECT assignee_id FROM system_vulnerabilities WHERE assignee_id IS NOT NULL);

ROLLBACK;

④ 확인 방법

not_in_rows
0
not_exists_rows
1
not_in_fixed
1

10-1은 검증할 때 상관 서브쿼리(약 55ms)가 JOIN + GROUP BY(약 85ms)보다 빨랐어요. 서브쿼리가 서버마다 system_id 인덱스로 바로 찾아가기 때문이에요. "서브쿼리는 느리다"는 통념과 다르게 나올 수 있으니, 추측하지 말고 재서 확인한다는 걸 결론으로 쓰면 돼요. 두 쿼리에 EXPLAIN을 붙여 차이의 이유도 캡처해 두세요.

⑤ 막히기 쉬운 부분

증상원인해결
ROLLBACK 후에도 임시 담당자가 남음GUI 도구가 자동 커밋(autocommit) 모드Workbench/DBeaver에서 자동 커밋을 끄거나, 터미널에서 실행
두 방식의 결과 행 수가 다름비교가 성립 안 함 (한쪽이 틀린 쿼리)시간 비교 전에 결과가 같은지 먼저 확인
