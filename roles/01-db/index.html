CAUTION · 주의할 점

  • 트리거는 누가 바꿨는지 몰라요. system_vulnerabilities.updated_by를 두고 트리거가 NEW.updated_by를 기록하게 하세요. ③과 미리 약속해야 합니다.
  • PK·FK 외에 추가 인덱스는 만들지 마세요. ②가 인덱스 전후 성능 비교를 할 거예요. UNIQUE도 인덱스를 자동으로 만들어요 (12주차: MySQL은 PK·FK·UK에 인덱스를 자동 생성). 그래서 UNIQUE 컬럼도 비교 실험 대상이 아니에요.
  • Debian 버전 문자열은 DB에서 크기 비교가 안 돼요. 영향 판정은 Python(④)이 하고, DB엔 근거(설치 버전, 수정 버전)를 저장합니다.
  • system_vulnerabilities는 파생 데이터가 아니에요. 담당자·기한·상태는 조인으로 만들 수 없는 업무 데이터라는 점을 발표에서 설명하세요.

PRESENT · 발표 대비: 12주차 용어로 정규화 설명하기

자세한 근거는 vuln-mgmt docs/design_decisions.md §1(정규화)에 있어요. 발표에서는 아래 세 문장을 12주차 용어 그대로 말하면 돼요.

  • 1NF: 모든 컬럼은 값 하나만 가져요. vulnerabilities는 CVE당 CVSS를 하나만 저장하고, 여러 출처·버전 중 무엇을 고르는지 규칙을 정해 뒀어요 (3.1 → 3.0 → 4.0 순서, 같은 버전이면 NVD 자체 점수 먼저 — ④ 가이드 5단계, 회의에서 확정). 고른 점수의 버전·출처는 cvss_version, cvss_source에 같이 남겨요. "점수가 여러 개인데 왜 컬럼 하나냐"는 질문에 이 규칙으로 답해요.
  • 2NF (부분 함수 종속 제거): cve_package_status의 PK는 (cve_id, software_id, ubuntu_release)예요. 소프트웨어 이름은 software_id 하나에만 종속되는 값(부분 함수 종속)이라 이 테이블에 두지 않고 software 테이블로 뺐어요.
  • 3NF (이행 함수 종속 제거): systems에 코드명(noble)을 두면 system_id → ubuntu_release → 코드명으로 이어지는 이행 함수 종속이 생겨요. 그래서 릴리스 번호(24.04)만 저장해요.
  • 이상 현상: 위처럼 나누지 않으면 소프트웨어 이름을 바꿀 때 여러 행을 고쳐야 하는 갱신 이상이 생겨요.
